# Нативное ядро TrustTunnelClient: своя сборка и патчи

CatTunnel работает не на официальном ядре TrustTunnelClient, а на собственной сборке того же ядра с патчами, и все платформы, начиная с 1.5.7, получают одну и ту же версию - 1.3.0-rc.1 (файл `ENGINE_VERSION` в корне, обновление командой `tools/update_engine.sh <версия>`). Главная доработка касается того, как первый пакет TLS-соединения (ClientHello) уходит в сеть: сам пакет остаётся одной TLS-записью, поэтому серверу ничего менять не нужно, однако фильтр провайдера видит его разрезанным или не по порядку. Приёмы заимствованы из [ByeDPI](https://github.com/hufrea/byedpi) (MIT, © 2024 hufrea), подробное описание режимов и своей строки - в [docs/anti-dpi.md](../../docs/anti-dpi.md).

## Что лежит в папке

| Путь | Назначение |
|---|---|
| `0001-anti-dpi-desync.patch` | анти-DPI: режимы 1-3, своя строка `-s/-o/-d`, причины отказа и паузы перед повтором, HTTP/2 padding, отключение QUIC |
| `build_linux.sh` | сборка ядра для Linux (без sudo) |
| `build_android.sh` | сборка `libtrusttunnel_android.so`, которую `tools/engine_patch/build.sh` кладёт в AAR вместо официальной |
| `windows/` | сборка для Windows |
| `router/` | сборка ядра для роутеров (zig) и патч монитора сети для систем с policy routing |
| `rc1/` | патчи для 1.3.0-rc.1: доработки ядра и раздельный туннель по программам на Windows и Linux |

## Сборка

Для Linux нужны conan 2.31.1, Rust 1.95 (профиль minimal), clang 19 с libstdc++; закрытый conan-репозиторий AdGuard не требуется, поскольку зависимости собираются скриптом `scripts/bootstrap_conan_deps.py` с повторным экспортом NativeLibsCommon 8.1.52. Первая сборка занимает около 17 минут, последующие проходят инкрементально. Для Android к этому добавляются gradle из исходного репозитория и cargo-ndk, а первая сборка arm64 длится около 25 минут, после чего пересборка укладывается в полминуты.

## Режимы анти-DPI

Ключ `anti_dpi_mode` в TOML (при `anti_dpi = true`) доходит до параметров TCP-сокета и до пинговалки (`ping.cpp`, `locations_pinger`), а сама отправка выполняется функцией `desync_write` в `net/src/tcp_socket.cpp`. Режим 0 повторяет поведение исходного ядра (первый байт, пауза 25 мс, остальное), режим 1 отправляет «срочный» байт после третьего байта и байты 4-7 с TTL 1 (`-o3 -d7` в синтаксисе ByeDPI), режим 2 отправляет первые 7 байт с TTL 1 (`-d7`), режим 3 ставит «срочный» байт и кусок с TTL 1 внутрь имени сервера (`-o1+s -d3+s`). Кусок с TTL 1 теряется на первом маршрутизаторе, и система отправляет его повторно уже с обычным TTL, так что фильтр видит остаток потока раньше начала.

Одиночный «срочный» байт без последующего куска с TTL 1 не допускается, и причина кроется в сервере. Сервер TrustTunnel на tokio читает ClientHello кусками по 1024 байта; чтение в Linux останавливается на OOB-метке и отдаёт один байт, tokio принимает короткое чтение за признак пустого сокета и снимает готовность, а остаток ClientHello к этому моменту уже лежит в очереди, и нового события не будет. Иными словами, сервер ждёт бесконечно, пока его не разбудит повторная отправка куска с TTL 1, которая приходит позже. Поэтому все режимы со «срочным» байтом идут в паре с TTL 1.

## Особенности Android

Кусок с TTL 1, отправленный сразу за пакетом со «срочным» байтом, ядро Android придерживает (TCP small queues) и отправляет уже после возврата обычного TTL, а запрос `SIOCOUTQNSD` приложению запрещён политикой SELinux. Решение заимствовано у sing-box: перед каждым следующим куском ядро ждёт подтверждения (`TCP_INFO.tcpi_unacked == 0`, не дольше 500 мс), а «отправлено» определяет по `tcpi_notsent_bytes`. Цена решения - один лишний круг по сети при установке соединения. На Windows ни «отправлено», ни подтверждение не измеряются, и вместо ожидания стоят паузы 10 и 50 мс.

## Отключение QUIC

Ключ `block_quic = true` в TOML проходит через `VpnUpstreamConfig` и `EndpointConnectionConfig` до `Tunnel::finalize_connect_action`, где UDP на порт 443 (кроме DNS) получает `VPN_CA_REJECT`. Браузеры после отказа переходят на TCP внутри туннеля; поведение покрыто тестом `TunnelTest.BlockQuic` (`core/test/test_tunnel.cpp`).

## Монитор сети на роутерах

Монитор сети NativeLibsCommon в Linux искал маршрут по умолчанию только в таблице `main`, тогда как при policy routing (Android, многие роутеры) маршруты разложены по отдельным таблицам правилами `ip rule`. В таких системах после любого события адреса или маршрута ядро решало, что сети нет (`VPN_SS_WAITING_FOR_NETWORK`), и само из этого состояния не выходило. Патч из `router/` заставляет `AutoNetworkMonitor` спрашивать ядро ОС напрямую (UDP `connect` к 8.8.8.8 или 2001:4860:4860::8888 и `getsockname`, правила при этом учитываются): если маршрут есть, «сети нет» не сообщается, а переподключение происходит только при смене адреса выхода.
