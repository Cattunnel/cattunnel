# Нативное ядро TrustTunnelClient: своя сборка и патчи

English: [README.en.md](README.en.md)

CatTunnel работает не на официальном ядре [TrustTunnelClient](https://github.com/TrustTunnel/TrustTunnelClient), а на собственной сборке того же ядра с патчами. Все платформы, начиная с 1.5.7, получают одну базовую версию, 1.3.0-rc.1 (файл `ENGINE_VERSION` в корне репозитория, хеши официальных настольных архивов в `ENGINE_SHA256`, смена версии командой `tools/update_engine.sh <версия>`). Ядро приложения 1.5.9.5 и роутера собрано из одной ревизии, `b59debf4` (`1.3.0-rc.1-57-gb59debf4`, то есть 57 коммитов поверх rc.1). В этом репозитории ревизия записана только в тексте [docs/anti-dpi.md](../../docs/anti-dpi.md); закрепляет её скрипт `engine/build_router.sh` в репозитории [cattunnel-router](https://github.com/Cattunnel/cattunnel-router) (переменные `REV` и `VERSION`, сборка прерывается, если ревизия другая).

Патчи в этой папке описывают ядро 1.3.0-rc.1. Изменения ревизии `b59debf4` сверх этих патчей (пул соединений, NineLives, формирователь набивки, браузерные заголовки `CONNECT`, ротация IP) сюда пока не выложены. Что делает ядро на уровне протокола, смотрите в [docs/](../../docs/).

Главная доработка этой папки касается того, как первый пакет TLS-соединения (ClientHello) уходит в сеть. Сам пакет остаётся одной TLS-записью, поэтому серверу ничего менять не нужно, но фильтр провайдера видит его разрезанным или не по порядку. Приёмы заимствованы из [ByeDPI](https://github.com/hufrea/byedpi) (MIT, © 2024 hufrea), режимы и своя строка описаны в [docs/anti-dpi.md](../../docs/anti-dpi.md).

## Сборка

Порядок на Windows закреплён в `windows/build_rc1.cmd`: клонировать тег `v1.3.0-rc.1`, применить `git apply --index` все `0*.patch` из папки патчей, собрать зависимости `scripts/bootstrap_conan_deps.py`, затем `cmake` и `ninja` с целью `trusttunnel_client`.

`build_linux.sh` делает для Linux следующее. Берёт `conan` и `cargo` из каталога сборки, клонирует `TrustTunnelClient` на тег `v1.1.7` и не применяет к нему патчи сам. Собирает зависимости через `scripts/bootstrap_conan_deps.py` без закрытого conan-репозитория AdGuard. Последним заново экспортирует NativeLibsCommon v8.1.52 (рецепт boringssl). Затем `cmake` с `clang`, `libstdc++11` и `-DDISABLE_HTTP3=OFF` и цель `trusttunnel_client`. Сборку пакета Linux принимает на вход готовый бинарник (`ENGINE_BIN`) и проверяет, что в нём есть строка `Anti-DPI mode` (`linux/packaging/build_release.sh`).

Для Android нужны всё то же, что для Linux, плюс NDK 29.0.14206865, JDK 17, цели Rust для четырёх ABI Android и `cargo-ndk`. `TT_ABIS` сужает список ABI (по умолчанию `arm64-v8a`). Скрипт собирает `assembleRelease` из чистого дерева (`TT_SRC`), копирует `libtrusttunnel_android.so` и печатает следующую команду: `NATIVE_JNI=<каталог> tools/engine_patch/build.sh`. Холодная сборка одного ABI занимает около 25 минут (комментарий в скрипте).

Для роутеров нужны zig 0.17.0, conan 2.31.1, NativeLibsCommon v8.1.52 и DnsLibs v2.10.2 из исходников с патчами из `router/` (zig-обёртка не узнаётся вложенными сборками зависимостей). `router/build_router.sh [архитектура...]` принимает `x86_64`, `aarch64`, `armv7`, `mips`, `mipsel` (по умолчанию `aarch64 mipsel armv7`), собирает статические musl-бинарники и проверяет, что в каждом есть строка `Anti-DPI mode`. Первая сборка под архитектуру занимает 30-40 минут (комментарий в скрипте), потом минуты. Скрипт в репозитории роутера (`engine/build_router.sh`) собирает уже ревизию `b59debf4`.

```text
 тег TrustTunnelClient v1.3.0-rc.1
        |  git apply rc1/0001-cattunnel-core.patch, rc1/0002-desktop-per-app-split.patch
        v
 дерево с патчами CatTunnel
        |-- cmake + ninja (Windows, MSVC)      -> trusttunnel_client.exe
        |-- cmake + ninja (Linux, clang)       -> trusttunnel_client  -> пакет Arch и Debian
        |-- gradle + cargo-ndk (build_android) -> libtrusttunnel_android.so -> AAR (tools/engine_patch)
        |-- zig + cmake (router/build_router)  -> статические бинарники для роутеров
```

## Режимы анти-DPI

Ключ `anti_dpi_mode` в TOML (при `anti_dpi = true`, значение зажимается в 0-3) попадает в параметры TCP-сокета и в пинговалку (`ping.cpp`, `locations_pinger`). Саму отправку выполняет функция `desync_write` в `net/src/tcp_socket.cpp`.

- Режим 0 повторяет поведение исходного ядра: первый байт, пауза 25 мс, остальное.
- Режим 1 (в синтаксисе ByeDPI `-o3 -d7`): «срочный» байт после третьего байта, затем байты с четвёртого по седьмой с TTL 1.
- Режим 2 (`-d7`): первые 7 байт с TTL 1.
- Режим 3 (`-o1+s -d3+s`): «срочный» байт и кусок с TTL 1 внутри имени сервера (SNI).

Ключ `anti_dpi_desync` принимает свою строку `-s<n>` (обычный TCP-разрез), `-o<n>` (срочные данные), `-d<n>` (TTL 1); позиция считается от начала записи, от конца при минусе или от имени сервера с суффиксом `+s`. Непустая строка заменяет `anti_dpi_mode`. Не принимаются `-r` (разрез TLS-записи: сервер её отвергает) и `-o` без `-d` после него.

Кусок с TTL 1 теряется на первом маршрутизаторе, ядро ОС повторяет его уже с обычным TTL, и фильтр видит остаток потока раньше начала.

```text
 ClientHello (одна TLS-запись), режим 1
   [байты 1-3] + 1 срочный байт  --send(MSG_OOB)-->
        ждём подтверждения предыдущего куска (до 500 мс)
   [байты 4-7]  --отправка с TTL 1--> теряется на первом маршрутизаторе
        TTL возвращается к прежнему
   [остаток]    --обычная отправка-->  ядро ОС повторяет потерянный кусок с обычным TTL
```

Рисунок 2. Порядок отправки ClientHello в режиме 1.

Одиночный «срочный» байт без следующего куска с TTL 1 не допускается: по комментарию в `desync_write` сервер TrustTunnel на tokio читает до метки срочных данных, короткое чтение принимается за пустой сокет, и остаток ClientHello, уже лежащий в очереди, никого не будит. Разбор отклоняет такой план, а если пара с TTL 1 отброшена из-за границ записи, «срочный» кусок уходит обычным разрезом. Повторно отправленный кусок с TTL 1 приходит позже и будит сервер.

Прочие ключи патча: `h2_padding_frames` (0-64: первые кадры HTTP/2 сессии получают случайную набивку до 255 байт, механизм PADDED из RFC 9113) и `block_quic` (см. ниже).

## Особенности Linux и Android

Кусок с TTL 1, отправленный сразу за пакетом со «срочным» байтом, ядро ОС может придержать (TCP small queues, замечено на Galaxy S22) и отправить уже после возврата обычного TTL. Решение, как в sing-box: перед каждым следующим куском ожидание подтверждения (`TCP_INFO.tcpi_unacked == 0`, не дольше 500 мс). Оно работает на Linux и Android. Затем TTL возвращается, когда ядро сообщило, что очередь пуста (до 20 мс): на Linux это запрос `SIOCOUTQNSD`, а на Android, где SELinux запрещает запрос приложению, поле `tcpi_notsent_bytes`. На Windows ни то ни другое не измеряется, вместо ожидания стоят паузы 10 и 50 мс.

## Причины отказа и паузы

Ядро различает три причины неудачного пинга и пишет их в журнал меткой `[failure=...]`: `connect` (нет TCP-соединения или QUIC не удался), `hello_reset` (ClientHello ушёл, соединение сброшено) и `hello_no_answer` (ClientHello ушёл, ответа нет: так выглядит «заморозка» адреса фильтром). Перед следующим рукопожатием ядро ждёт не меньше 60 секунд после `hello_no_answer` и 5 секунд после `hello_reset`; после `connect` дополнительной паузы нет. Приложение читает метку, чтобы подсказать пользователю, что делать.

## Отключение QUIC

Ключ `block_quic = true` в TOML проходит через `VpnUpstreamConfig` и `EndpointConnectionConfig` до `Tunnel::finalize_connect_action`, где UDP на порт 443 получает `VPN_CA_REJECT`. Браузеры после отказа переходят на TCP внутри туннеля. Поведение покрыто тестом `TunnelTest.BlockQuic` (`core/test/test_tunnel.cpp`).

## Раздельный туннель по программам

Патч `rc1/0002` добавляет ключи `excluded_apps` и `included_apps` в `[listener.tun]` (имена исполняемых файлов или полные пути). Перечисленные в `excluded_apps` программы идут напрямую, при непустом `included_apps` через туннель идут только перечисленные. Владельца сокета находит `process_owner.cpp`: на Windows через `GetExtendedTcpTable` и `GetExtendedUdpTable`, на Linux через `NETLINK_SOCK_DIAG` и `/proc/<pid>/fd`, драйвер не нужен.

## Монитор сети на роутерах и Android

Монитор сети NativeLibsCommon в Linux искал маршрут по умолчанию только в таблице `main`. При policy routing (Android, многие роутеры) маршруты лежат в отдельных таблицах, и после любого события адреса или маршрута клиент решал, что сети нет (`VPN_SS_WAITING_FOR_NETWORK`), и сам из этого состояния не выходил. Патч заставляет `AutoNetworkMonitor` спрашивать ядро ОС напрямую: UDP-сокет с `connect` на 8.8.8.8 (при неудаче на `2001:4860:4860::8888`) и `getsockname`, правила при этом учитываются. Если маршрут есть, «сети нет» не сообщается, а переподключение происходит только при смене исходящего адреса. Эта правка уже входит в `rc1/0001`; отдельный `router/0002-network-monitor-policy-routing.patch` нужен для базы без `rc1/`.
