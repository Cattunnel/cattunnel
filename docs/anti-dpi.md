# Анти-DPI в CatTunnel

Фильтр провайдера (ТСПУ) читает имя сервера (SNI) в первом пакете TLS-соединения — ClientHello. Анти-DPI меняет только то, как этот пакет уходит в сеть: сам ClientHello остаётся одной TLS-записью, поэтому серверу ничего менять не нужно. Работает только с HTTP/2 (TCP); для HTTP/3 (QUIC) настройка ни на что не влияет.

Реализация — собственная сборка нативного ядра TrustTunnelClient с патчем `tools/engine_native/0001-anti-dpi-desync.patch` (функции `desync_write` и `desync_plan_parse` в `net/src/tcp_socket.cpp`). Приёмы заимствованы из [ByeDPI](https://github.com/hufrea/byedpi) (MIT, © 2024 hufrea).

## Режимы

В настройках ключа, раздел «Обход блокировок», меню «Анти-DPI»:

| Пункт | В БД (`servers.anti_dpi`, `anti_dpi_mode`) | Что уходит в ядро | Что делает |
|---|---|---|---|
| Выкл | `false`, — | ничего | пакет уходит целиком |
| Обычный | `true`, 0 | `anti_dpi = true` | апстрим: первый байт, пауза 25 мс, остальное |
| Авто | `true`, 4 | режим 1, 2 или 3 | перебирает 1 → 2 → 3, запоминает удачный для сервера и сети (`anti_dpi_auto.dart`) |
| 1 | `true`, 1 | `anti_dpi_mode = 1` | `-o3 -d7` |
| 2 | `true`, 2 | `anti_dpi_mode = 2` | `-d7` |
| 3 | `true`, 3 | `anti_dpi_mode = 3` | `-o1+s -d3+s` |
| Своя строка | `true`, 5 + `anti_dpi_desync` | `anti_dpi_desync = "…"` | см. ниже |

Режимы 1–3 в ядре — это готовые строки, поэтому они и своя строка выполняются одним кодом.

## Своя строка

Части пишутся через пробел и выполняются по порядку, частей не больше восьми.

- `-s N` — обычный разрыв TCP после байта N.
- `-o N` — разрыв со «срочным» байтом: кусок до N уходит через `send(MSG_OOB)` вместе с одним лишним байтом, который ядро ОС получателя изымает из потока.
- `-d N` — кусок до байта N уходит с TTL (hop limit) 1. Он теряется на первом маршрутизаторе, потом ОС отправляет его повторно уже с обычным TTL, так что фильтр видит остаток потока раньше начала.

N отсчитывается от начала TLS-записи. Отрицательное N считается от её конца, а с суффиксом `+s` — от начала имени сервера в SNI (`+h` для TLS означает то же самое). Если SNI в пакете не нашёлся, а в строке есть позиции с `+s`, применяется режим 1. Части, которые не попадают строго внутрь записи после предыдущей, пропускаются.

Ограничения:

- `-r` (разбиение на TLS-записи) не принимается: сервер TrustTunnel такой ClientHello отвергает. Поддержка на сервере — пункт C плана 1.5.0.
- `-o` без `-d` после него не принимается. Сервер TrustTunnel на tokio зависает: чтение останавливается на OOB-метке, tokio считает сокет пустым, а остаток уже в очереди и нового события не будет. Повторная отправка куска с TTL 1 приходит позже и будит сервер. Если `-d` после `-o` выпал при разметке конкретного пакета, этот `-o` отправляется как обычный разрыв.
- Из других приёмов ByeDPI (`-f` fake, `-q` и т. п.) пока ничего не поддерживается.

Примеры: `-o1+s -d3+s` (режим 3), `-d7` (режим 2), `-o3 -d7` (режим 1), `-s1 -d3+s`.

Строку проверяют три одинаковых набора правил: `DesyncString.validate` (плагин, форма ключа, ссылки), `desync_plan_parse` (ядро) и тесты с обеих сторон (`plugins/vpn_plugin/test/desync_string_test.dart`, `net/test/test_desync_plan.cpp`). Ядро отклоняет ключ с неверной строкой целиком, а не подключается молча без обхода; приложение до этого не доходит — форма не сохраняет такую строку, а из ссылок и подписок неверная строка отбрасывается.

## Откуда берётся настройка

- Форма ключа — сохраняет строку в нормализованном виде (одиночные пробелы).
- Ссылка `tt://`: тег `0x41` — режим (1–4), `0x42` — отпечаток TLS, `0x43` — своя строка (UTF-8). Если тега нет, приложение оставляет выбор пользователя. Старые версии приложения неизвестные теги пропускают.
- Подписка: при синхронизации режим и строка обновляются, только если ссылка их называет.
- Отчёт о проблеме показывает режим, а для своей строки — саму строку.

## Маскировка размеров (HTTP/2 padding)

`h2_padding_frames = N` (0–64; ключ, «Для экспертов»; тег `0x44` в `tt://`): первые N кадров HEADERS/DATA каждой HTTP/2-сессии получают флаг PADDED и 0–255 случайных байт (`select_padding_callback` в `net/src/http2.cpp`). Приложение ставит 8 или 0, по умолчанию выключено. Padding — часть стандарта HTTP/2 (RFC 9113, 6.1), сервер ничего не настраивает.

Проверено 03.10 на тестовом ноутбуке: сервер TrustTunnel 1.1.0 (как на main, крейт `h2` 0.3), клиент и сервер на 127.0.0.1, запрос через туннель — 200 в обоих режимах. Байт от клиента к серверу: 2173 без padding и 2578 с N = 16 (кадр 85 → 309 байт, плюс ещё один на 276).

## Отключить QUIC

`block_quic = true` (ключ, «Для экспертов»; тег `0x45` в `tt://`, однобайтовый bool): ядро отклоняет каждое UDP-соединение на порт 443, кроме DNS (`Tunnel::finalize_connect_action` в `core/src/tunnel.cpp`, действие `VPN_CA_REJECT`). Браузеры и YouTube после отказа QUIC переходят на TCP внутри туннеля. Сделано для проверки, не тормозит ли QUIC-внутри-туннеля; серверу ничего настраивать не нужно. Тест `TunnelTest.BlockQuic`. Подписка может только включить, бот тег пока не выдаёт.

## Отказы и «заморозка»

Когда ни один адрес сервера не ответил, ядро определяет причину (`PingFailure` в `net/utils.h`) и дописывает её в текст ошибки тегом `[failure=…]`:

| Тег | Что было | Пауза ядра перед следующим рукопожатием |
|---|---|---|
| `connect` | TCP не установился (отказ, недоступен, таймаут) или не прошёл QUIC | как в апстриме |
| `hello_reset` | TCP есть, ClientHello ушёл, соединение сброшено или закрыто — блок по SNI или отказ сервера | 5 с (апстрим повторял через ~10 мс, а пачка рукопожатий с такими промежутками сама вызывает заморозку) |
| `hello_no_answer` | TCP есть, ClientHello ушёл, ответа нет — так выглядит «заморозка» адреса фильтром | 60 с (по отчётам о ТСПУ лета 2026, каждое рукопожатие во время заморозки её продлевает) |

Классификация живёт в `ping.cpp` (ушёл ли ClientHello — `tcp_socket_hello_sent`), пауза — `handshake_pause` в `vpn_fsm.cpp`. Проверено локально, на 127.0.0.1, тремя заглушками: порт закрыт, порт молчит, порт сбрасывает соединение.

До приложения тег доходит так. На Android ядро после каждой неудачной попытки поднимает событие `VPN_EVENT_PING_FAILED` (в том числе пока идёт первое подключение, когда состояние между попытками не меняется), JNI-слой (`lib.cpp`, `onPingFailed`) отправляет запись `{"cattunnel_failure":"…"}` через `onConnectionInfo`, а плагин переправляет её в отдельный канал `vpn_plugin_event_channel_failures`. На Linux helper находит тег в выводе CLI (`cli_output.h`, `ParseFailure`) и шлёт событие `failure`. Официальное ядро тегов не пишет, поэтому с ним поток пуст.

Приложение (`ConnectFailures`, `VpnScope`):

- «Авто» при `hello_reset` переходит к следующему способу (с паузой 1,5 с). При `hello_no_answer` и `connect` способы больше не перебираются: ядро продолжает тем же способом и само выдерживает паузу. Если адрес «заморожен» меньше двух минут назад, новый старт пробует только первый способ.
- Диагностика Марсика при заморозке не делает своих TLS-проверок к этому адресу. Она сразу говорит «адрес заморожен, жду» и ищет другой рабочий сервер (у другого сервера другой адрес, одно рукопожатие туда не вредит).

## Ограничения платформ

- Android: ОС не даёт приложению `SIOCOUTQNSD`, поэтому «отправлено» определяется по `TCP_INFO.tcpi_notsent_bytes`. Перед каждой следующей частью ядро ждёт ACK (`tcpi_unacked == 0`, до 500 мс), это +1 RTT к установке соединения.
- Своё ядро с этим патчем выходит с 1.4.6 для всех ABI Android, для Windows и Linux. Изменения 1.5.0 (своя строка, причины отказа, паузы, padding, отключение QUIC) собраны для Linux и для Android arm64 (бета 1.5.0); Windows и остальные ABI Android — ещё нет.
- Windows: код OOB и TTL тот же, но ни «отправлено», ни ACK там не измеряются — вместо ожидания стоят паузы 10 и 50 мс.
