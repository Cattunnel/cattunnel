# Протоколы CatTunnel

Инженерная спецификация форматов обмена, редакция 24.11.2026 (выпуск 1.5.9.5). Для параметров конкретного сервера используются только `example.com`, `/<путь>` и `<секрет>`. Ссылки вида `файл:строка` относятся к исходному дереву указанного компонента: серверное дерево есть [cattunnel-server](https://github.com/Cattunnel/cattunnel-server), репозиторий приложения есть этот репозиторий, репозиторий движка есть сборка TrustTunnelClient с патчами CatTunnel (часть патчей лежит в `tools/engine_native/` и `tools/engine_patch/`, остальные ещё не выложены, поэтому ссылки на `core/` и `net/` пока не проверить по открытым исходникам).

Термины. Endpoint есть серверный процесс (Rust), принимающий TLS и HTTP/2; клиентский движок есть нативная часть приложения (C++), которая держит соединения. Путь отсчитывается от корня названного репозитория. Нумерация таблиц и рисунков сквозная по всему документу, поэтому таблица с номером П.3 может стоять в разделе П.2.

Границы документа. Здесь описано то, что видно на проводе и в ссылке: форматы, порядок обмена, проверки и умолчания. Не описаны побайтно профили ClientHello (их задаёт движок, а сверяют захватом трафика), параметры HTTP/2 SETTINGS, политика повторной передачи и частота ACK в NineLives, внутреннее устройство сервера подписок. Для них источником остаётся код и полные спецификации компонентов: `PROTOCOL.md` и `docs/xhttp-protocol.md` серверного дерева, `docs/anti-dpi.md` и `docs/padding.md` приложения.

## П.1. Транспорт TrustTunnel

Клиент открывает TLS-соединение к endpoint с ALPN `h2`; внутри HTTP/2 отдельный поток `CONNECT` обслуживает TCP-соединение назначения. Условие успеха: проверенный сертификат, допустимые учётные данные и ответ HTTP 200. Псевдоцель есть служебное имя в `:authority`, начинающееся с подчёркивания: `_udp2` выбирает обработчик UDP, `_icmp` обработчик ICMP, `_check` проверку живости; во всех остальных случаях в поле стоит `host:port` назначения. Пул клиента держит два-четыре TLS-соединения и открывает новое, когда на каждом уже 24-48 потоков; между рукопожатиями пауза 2-6 с, не больше трёх в минуту (`docs/anti-dpi.md:60-71` репозитория приложения).

*Таблица П.1. Поля HTTP/2-запроса CONNECT (имена заголовков, без фиксированных смещений HPACK)*

| Поле | Длина | Значение |
|---|---|---|
| `:method` | переменная | `CONNECT` |
| `:authority` | переменная | `example.com:443`, псевдоцель `_udp2`, `_icmp` или `_check` |
| `user-agent` | переменная | идентификатор платформы и клиента |
| `proxy-authorization` | переменная | `Basic ` + base64 от UTF-8 `логин:пароль` |

```text
 client                       endpoint                   target
   |--- TLS 1.3, ALPN h2 -------->|                       |
   |--- CONNECT example.com:443 ->|--- TCP connect ------>|
   |<-- HTTP 200 + headers -------|<-- connected ----------|
   |=== DATA ====================>|=== bytes =============>|
   |<== DATA =====================|<== bytes ==============|
   |--- END_STREAM / RST_STREAM -->|                       |
```

*Рисунок П.1. Открытие и завершение TCP-потока*

Успешный ответ серверного endpoint, форка TrustTunnel, содержит `date`, `server`, `cache-control: no-cache, no-store, must-revalidate`, `x-request-id`, `x-trace-id` без `content-length` и `transfer-encoding`. Сервер режет данные ответа на DATA по 4096 байт: эти 4096 байт считаются без заголовка HTTP/2 (`docs/features.md:37-43`, `lib/src/http2_codec.rs`). При ошибке авторизации endpoint отвечает заданным в `vpn.toml` (конфигурация серверного endpoint) кодом из 407/405/404/403. Ответ 407 клиентский движок классифицирует как фатальный отказ авторизации; 405/404/403 не открывают поток, но сами по себе не позволяют клиенту отличить неверный пароль от другого отказа (`core/src/http2_upstream.cpp:209-215`, `CONFIGURATION.md:292-303`). `_check` есть служебная псевдоцель CONNECT для проверки живости, её успешный ответ равен HTTP 200 (`PROTOCOL.md:393-423`).

UDP использует один отдельный CONNECT к `_udp2` и последовательность записей внутри него. Запись есть непрерывная последовательность байтов потока: она может пересекать границы HTTP/2 DATA, и приёмник дочитывает её из следующих DATA. Смещения отсчитываются от начала записи, целые без знака в сетевом порядке. Ответный формат не содержит имени приложения (`PROTOCOL.md:263-320`).

*Таблица П.2. UDP-запись клиент → endpoint*

| Смещение | Поле | Длина | Значение |
|---|---|---|---|
| 0 | length | 4 | число байт после самого поля length: 37 + L + длина payload (вся запись 41 + L + payload) |
| 4 | source IP | 16 | IPv4 с 12 ведущими нулями или IPv6 |
| 20 | source port | 2 | порт источника |
| 22 | destination IP | 16 | адрес назначения |
| 38 | destination port | 2 | порт назначения |
| 40 | app-name length | 1 | L, длина имени в следующем поле |
| 41 | app-name | L | имя приложения |
| 41 + L | payload | остаток | UDP-датаграмма |

В ответе поле длины так же не считает себя и равно 36 + длина payload; после него следуют source IP (16), source port (2), destination IP (16), destination port (2) и payload без имени приложения. Запись с полем length меньше 37 отклоняется; неверная длина имени или неверный UTF-8 приводят к пропуску объявленной записи (`lib/src/http_udp_codec.rs:24-34,82-165`). Адрес с двенадцатью ведущими нулевыми байтами декодируется как IPv4, иначе как IPv6 (`lib/src/net_utils.rs:117-135`).

ICMP при включённой секции `[icmp]` того же серверного `vpn.toml` идёт через CONNECT `_icmp`: запрос фиксированного размера 23 байта содержит `id:u16` при смещении 0, destination IP (16 байт) при 2, `sequence:u16` при 18, `ttl:u8` при 20 и `data_size:u16` при 21. Ответ фиксированного размера 22 байта содержит `id:u16` при 0, source IP (16) при 2, `type:u8` при 18, `code:u8` при 19 и `sequence:u16` при 20. Целые в сетевом порядке. Границы сообщений задаёт только фиксированный размер 23 или 22 байта, а не границы HTTP/2 DATA. Поле `data_size` задаёт длину эхо-данных, которые сервер создаёт сам: тело ICMP-запроса клиент не передаёт, сервер подставляет `data_size` случайных байтов (`lib/src/http_icmp_codec.rs:19-32,44-76,82-126`). Клиент, в котором UDP или ICMP не включён, не открывает соответствующий псевдопоток; аутентификация нужна и для них.

## П.2. TLS, имя и ключ в ClientHello

Перед HTTP/2 клиент предъявляет TLS ClientHello с SNI хоста и выбирает профиль имитации браузера. Сервер сопоставляет SNI с `hostname` или `allowed_sni` из `hosts.toml`, а ключ проверяет по `rules.toml`; оба файла принадлежат серверному endpoint. Клиент проверяет сертификат сервера для SNI этого соединения (`docs/features.md:41-75` серверного дерева, `core/src/vpn_manager.cpp:827-846`). Ротация имени без сертификата, покрывающего новое имя, приводит к отказу на клиенте.

*Таблица П.3. Существенные поля ClientHello (TLS-формат стандартный)*

| Поле | Длина | Значение |
|---|---|---|
| TLS record header | 5 | тип записи и её длина |
| ClientHello.random | 32 | 16 байт соли и 16 байт подтверждения в режиме ключа либо 32 случайных байта без него |
| SNI extension | переменная | имя, по которому проверяются сертификат и ключ |
| ALPN extension | переменная | `h2` |

```text
 client                                  endpoint
   |-- ClientHello: SNI, random[32] -------->|
   |   random[0:16]  = fresh salt            |-- hosts.toml: match SNI
   |   random[16:32] = AES-128-ECB(          |-- rules.toml: rule
   |     SHA256(SNI)[0:16],                  |
   |     HKDF(key, salt=random[0:16]))       |-- recompute random[16:32]
   |                                         |   and compare
   |<-- ServerHello, Certificate, Finished --|
   |-- verify certificate for SNI ---------->|
```

*Рисунок П.2. Проверка ключа, привязанного к SNI*

Точные байты для режима `client_random_auth_key`: первые 16 случайны, последние 16 равны `AES-128-ECB(SHA256(SNI)[0:16], HKDF-SHA256(secret=key, salt=random[0:16]))`; первый аргумент AES есть открытый текст, второй ключ шифрования. Имя из этого ClientHello участвует в вычислении, поэтому смена SNI меняет проверочный блок. Правила просматриваются по порядку, и действует действие первого совпавшего. Правило совпадает, когда выполнены все заданные в нём условия: `cidr` для адреса клиента и одно из условий по `random`. Если заданы и префикс, и auth-ключ, проверяется только ключ. Совпадений нет, значит соединение разрешено: умолчание есть `allow`. При наличии хотя бы одного auth-key-правила соединение без SNI или без `random` отклоняется сразу (`CONFIGURATION.md:488-549`). Старый `client_random_prefix` задавал постоянные байты в начале `random`; новые ссылки его не выдают, декодер приложения игнорирует тег `0x0B` (`plugins/vpn_plugin/lib/domain/deep_link_payload_codec.dart:429-431`).

Серверный приёмник собирает ClientHello из нескольких TLS-записей, прежде чем разобрать SNI и `random`. Клиентские режимы Анти-DPI в выпуске делят одну TLS-запись на TCP-сегменты и не включают деление на отдельные TLS-записи: приём таких записей на сервере оставлен в запасе (`docs/features.md:41-45`, `docs/anti-dpi.md:46-50`). Профили Chrome 157 и Firefox 160 относятся к версии клиентского движка; имя профиля само не означает побайтного совпадения с браузером, и профиль проверяется захватом на проводе. При неверном сертификате текущего сервера клиентский движок прекращает подключение (`core/src/vpn_manager.cpp:827-846`).

## П.3. Ротация точек входа

Ключ подключения (одна ссылка `tt://`) может нести основной адрес A и дополнительные адреса с собственными наборами SNI. По окончании случайно выбранного срока на A клиентский движок берёт следующий доступный адрес по кругу, открывает отдельное TLS-соединение к кандидату B и проверяет сертификат по SNI этого соединения. Длительность срока задают нижняя и верхняя границы в секундах. Новые потоки переводятся только после успешного первого запроса через B; прежние доживают на A (`docs/rotation.md:3-36` репозитория приложения, `core/src/upstream_multiplexer.cpp`).

*Таблица П.4. Поля ротации в ссылке (см. П.4)*

| Тег | Тип | Значение |
|---|---|---|
| `0x53` | последовательность строк | один адрес `host:port` и альтернативные SNI этого адреса через пробел; длина каждого элемента есть varint |
| `0x54` | varint | нижняя граница срока активного адреса, секунды |
| `0x55` | varint | верхняя граница срока активного адреса, секунды |

```text
 A active -- term expires --> new TLS to B, cert by B's SNI
                                |
                                +-- B opens, first request OK --> B active
                                +-- B refuses cert or password --> B rests
                                |                                  A active
                                +-- B silent --> one probe to A
                                                   | A answers: B rests
                                                   | A silent: network
                                                   |            backoff
 A silent mid-term --> next available address at once
```

*Рисунок П.3. Подготовка кандидата до переключения*

Элемент списка `0x53` есть строка UTF-8 `host[:port] [sni ...]`, части разделены пробельными символами. Порт без указания берётся у первого адреса ключа (443, если адреса нет). В списке не больше 16 элементов и не больше 8 имён в элементе; повтор адреса отбрасывается, повтор имени считается один раз, элемент с неверным адресом или хотя бы одним неверным именем пропускается целиком (`plugins/vpn_plugin/lib/domain/rotation_addresses.dart:12-19,84-128`). Границы `0x54` и `0x55` заданы в секундах: 0 значит «не задано», иначе приложение приводит значение к 60..86 400 и пишет теги только вместе с непустым `0x53`. Если нижняя граница не задана, движок берёт срок сессии (тег `0x4E`); если не задан и он, срока нет, и ключ уходит с адреса только тогда, когда тот перестаёт отвечать. Верхняя граница меньше нижней поднимается до нижней. Старый и новый пул соединений после переключения живут вместе 10 % от середины диапазона, но не меньше 1 с: при 600-900 с это 75 с (`core/src/upstream_multiplexer.cpp:805-835`).

Кандидат, не открывший соединение, в том числе из-за сертификата или пароля, отдыхает случайные 5-10 минут, а ключ остаётся на A. Если отдыхают все адреса, следующая попытка ждёт ближайшего конца отдыха. Когда молчат и кандидат, и исходный адрес, паузы сети составляют 1/4/9/16/20 минут без назначения отдыха. Отказ сертификата или пароля на уже активном адресе фатален: туннель выключается (`docs/rotation.md:18-37`, `core/src/vpn_fsm.cpp:242-281,446-477`). Новый запуск снова начинает с A, но отметки отдыха живут только в памяти процесса (`core/src/vpn_manager.cpp:95-96`). Ротация действует только для CONNECT; при NineLives (П.6) список адресов не применяется (`core/src/vpn_manager.cpp:129-132`). Сервер подписок CatTunnel выдаёт теги `0x53`-`0x55` по заголовку `x-app-version` начиная с клиента 1.5.9.5, а при неизвестной версии не выдаёт.

## П.4. Ссылка `tt://`

Приложение импортирует `tt://?` с полезной нагрузкой base64url без `=` сразу после вопросительного знака; декодер принимает также форму без `?`. Тело есть последовательность TLV, где порядок тегов не задан. Тег и длина суть целые QUIC varint, у которых первые два бита задают длину числа 1/2/4/8 байт; за ними идут ровно `length` байт значения. Строка есть UTF-8 без завершающего нуля. Список строк (`string[]`) есть просто подряд записанные элементы `varint length + UTF-8`: счётчика элементов нет, конец списка задаёт длина TLV. Тип `byte` есть TLV длины ровно 1, `bool` то же со значением 00 или 01. Значение `0x08` есть DER всех сертификатов цепочки, записанные подряд без разделителей (`deep_link_payload_codec.dart:203-230`). Тег `0x02` повторяется отдельным TLV для каждого адреса, теги `0x0D`, `0x52`, `0x53` содержат по одному TLV со списком элементов вида `varint length + UTF-8` (`plugins/vpn_plugin/lib/domain/deep_link_payload_codec.dart:29-109,203-208,242-265,283-297`).

*Рисунок П.4. Разбор ссылки без знания будущих тегов*

Релизный код приложения выдаёт версию 1 и отвергает значение больше 1, требует hostname, хотя бы один address, username и password. Усечённое TLV, неверный base64url, UTF-8 или bool приводят к отказу; незнакомый тег в принятой версии 1 пропускается по объявленной длине, а `0x0B` дополнительно игнорируется. Теги `0x46`-`0x4B` и `0x53`-`0x59` проверяются по типу и диапазону: число с лишними байтами или больше предела делает ссылку недействительной. Пределы: `0x46` до 64 кадров, `0x48` и `0x49` до 256 байт, `0x4A` и `0x4B` до 1 048 576 байт, `0x4C` до 3600 с, `0x4E` до 86 400 с, `0x54` и `0x55` до 86 400 с; `0x41` вне 1-4 считается отсутствующим (режим по умолчанию) (`plugins/vpn_plugin/lib/domain/deep_link_payload_codec.dart:111,328-445,501-550`). Серверный справочник `DEEP_LINK.md:6-21,93-115` описывает версию 2 с `subscription_url` (`0x0E`) и числовым `tls_profile` (`0x10`). Ссылку версии 2 приложение отвергает по номеру версии, поэтому серверный экспорт нельзя без проверки считать совместимым с приложением 1.5.9.5. Теги `0x0E` и `0x10` обозначены как версия 2: в таблице они даны для полноты, но в версии 1 не действуют. Точная версия каждого расширения до 1.5.9 в источниках не закреплена, и таблица отмечает лишь подтверждённые границы.

## П.5. Подписка

Сервер подписок выдаёт текст со ссылками `tt://`, по одной на строку, и необязательной строкой `#mirrors` со списком HTTPS-зеркал. Если клиент прислал ключ устройства, сервер шифрует ответ age для него; после расшифровки получается тот же текст. Это не то же, что upstream-подписка самого endpoint: endpoint отдаёт JSON (`docs/subscriptions.md:3-28` репозитория приложения; `CONFIGURATION.md:424-463` серверного дерева).

*Таблица П.6. Поля обмена с сервером подписок проекта; JSON первичной выдачи описан в тексте ниже*

| Поле | Длина | Значение |
|---|---|---|
| GET HTTPS | переменная | адрес с токеном в пути, без перенаправлений |
| `user-agent` | переменная | `CatTunnel/<версия>` |
| `x-device-key` | переменная | публичный age-ключ устройства, base64 |
| `x-hwid` | переменная | случайный идентификатор устройства |
| `x-device-os`, `x-device-model`, `x-ver-os` | переменная | сведения об устройстве |
| `x-app-version` | переменная | версия приложения для выдачи совместимых тегов |
| response body | переменная | age binary/armor либо текстовые строки `tt://` |

```text
 issuer -- link with one-time code --> application
 application -- POST code + device_key --> subscription service
 application <-- URL + initial mirrors --- subscription service
 application -- GET + x-device-key -----> first mirror
 application <-- age( #mirrors + tt://... ) or text
 application -- decrypt, then import ----> local server list
```

*Рисунок П.5. Первичный обмен и обновление*

Для первичной выдачи приложение извлекает код из одноразовой ссылки, отправляет JSON `{code, device_key, device_id, platform, model, os_version}` в `POST /api/ct/exchange` и получает `{subscription, mirrors}`: постоянный адрес и начальный порядок зеркал; код расходуется. При регулярном опросе зеркала перебираются до первого HTTP 200; на соединение и заголовки отводится 7 с, чтение тела 20 с, тело больше 4 МБ отклоняется; 408/429/5xx повторяются (`docs/subscriptions.md:30-39`). Закрытый ключ age хранится на устройстве.

При обновлении серверы сверяются по имени в пределах подписки; пропавшие удаляются, кроме текущего выбранного в интерфейсе, а ответ без строк `tt://` считается ошибкой. Строка `#mirrors` заменяет сохранённый порядок зеркал для следующего опроса; незнакомые строки пропускаются (`docs/subscriptions.md:17-19,43-59`). Имена HTTP-заголовков не различают регистр, поэтому `x-hwid` и `X-HWID` есть одно поле.

## П.6. NineLives

NineLives есть расширение того же TLS/HTTP/2 endpoint: одна TCP-сессия передаётся двумя потоками с одинаковым `/<путь><sid>`, где GET несёт данные сервер → клиент, а POST данные клиент → сервер. Версия 1 требует в каждом из двух запросов ровно один заголовок `x-xhttp-version` со значением `1`; повтор заголовка, ведущий ноль в числе, отсутствие и неизвестная версия дают HTTP 400 без спаривания. SID есть строка из 1-64 символов ASCII: латинские буквы, цифры, `-`, `_`. Авторизация обеих половин предшествует соединению (`docs/xhttp-protocol.md:8-31` серверного дерева).

*Таблица П.7. Формат кадра NineLives, целые big-endian*

| Смещение | Поле | Длина | Значение |
|---|---|---|---|
| 0 | type | 1 | номер типа кадра |
| 1 | offset | 8 | смещение payload в пределах своего направления, от 0 |
| 9 | short_length | 2 | длина 0-32767; старший бит 0x8000 означает, что длина лежит в `long_length` |
| 11 | long_length | 4, только при флаге | полная длина payload |
| 11 или 15 | payload | length | тело кадра |

Типы: `0x01` OPEN (payload `host:port`), `0x02` DATA, `0x03` ACK, `0x04` FIN, `0x05` RST, `0x06` PAD, `0x07` RESUME, `0x08` PING, `0x09` PONG, `0x0A` HELLO, `0x0B` HELLO_ACK, `0x0C` RESUME_TOKEN. Неизвестный тип закрывает обмен; предел буферизованного кадра 2 МиБ (`docs/xhttp-protocol.md:33-73`). Границы кадров задаёт только поле длины, а не границы HTTP/2 DATA или TLS-записей.

```text
 client                               endpoint
   |--- GET /<путь><sid>, version:1 ---->|
   |--- POST /<путь><sid>, version:1 --->|
   |--- HELLO (if server key set) ------->|
   |<-- HELLO_ACK (encrypted mode) ------|
   |--- OPEN host:port ----------------->|-- TCP --> target
   |<-- RESUME_TOKEN --------------------|
   |<=> DATA / ACK / FIN <=============>|
   |    break: new pair GET/POST         |
   |<-- GET header: challenge ----------|
   |--- POST body: RESUME(HMAC) -------->|
```

*Рисунок П.6. Фазы обычной и возобновлённой сессии*

Если клиент имеет настроенный публичный ключ сервера Ed25519, шифрованный режим, он же набор шифрования 1, начинается открытым HELLO: `suite:u16 = 1`, `caps:u32 = 0`, одноразовый публичный ключ X25519 клиента (32 байта), nonce клиента (16). HELLO_ACK несёт те же `suite` и `caps`, одноразовый публичный ключ X25519 сервера (32) и подпись Ed25519 (64). Без настроенного ключа клиент пропускает HELLO, и OPEN вместе со следующими кадрами идёт открыто внутри TLS. Подписываемая стенограмма равна ASCII `cattunnel-xhttp-handshake-v1` || version:u16(1) || suite:u16(1) || caps:u32(0) || ASCII(sid) || client_public[32] || server_public[32] || client_nonce[16], целые big-endian. Соль HKDF-SHA256 равна SHA256(стенограмма), входной ключевой материал есть общий секрет X25519, info `cattunnel-xhttp-v1 c2s` и `cattunnel-xhttp-v1 s2c`, ключи AES-128-GCM по 16 байт. После HELLO и HELLO_ACK каждый полный кадр упаковывается в запись `ciphertext_length:u32 || ciphertext || tag[16]`; длина включает тег, но не четырёхбайтный префикс, и лежит в пределах 16..1048592. AAD равен байтам SID без завершающего нуля, nonce `direction:u8 || 00 00 00 || counter:u64`, где направление 1 есть клиент → сервер, а 2 сервер → клиент; счётчики независимы и начинаются с нуля, значение `u64::MAX` не используется. Неверные подпись, ключ, набор или тег AEAD не дают перехода на открытое тело (`docs/xhttp-protocol.md:75-129`, `lib/src/xhttp_crypto.rs`).

При первом OPEN сервер отправляет RESUME_TOKEN из 32 случайных байт. Замещающий GET с тем же SID получает в заголовке `x-xhttp-challenge` 32 байта в standard base64. RESUME в теле POST содержит `up_confirmed:u64 || down_received:u64 || proof[32]`, где `proof = HMAC-SHA256(token, ASCII("cattunnel-xhttp-resume-v1") || ASCII(sid) || up_confirmed || down_received || challenge)`. Поле `up_confirmed` есть число подтверждённых байтов направления клиент → сервер, `down_received` число принятых байтов направления сервер → клиент; оба значат следующий ожидаемый offset. Неверное доказательство даёт HTTP 403, и старая пара GET/POST продолжает работать; недопустимые смещения отвергаются до переключения. Шифрованная сессия проводит для новой пары новый HELLO, получает новые ключи и нулевые счётчики, а RESUME передаёт внутри AEAD. `FIN` загрузки подтверждается `ACK` с тем же offset и payload `[0x04]`; пока подтверждения нет, память для повторной передачи сохраняется (`docs/xhttp-protocol.md:132-189`).

Настройки сервера: `xhttp_enable = false` по умолчанию; `xhttp_resume_timeout = 60` секунд, где 0 запрещает возобновление; список поддерживаемых версий `[1]`. Бюджет памяти по умолчанию есть четверть меньшего из двух значений, физической памяти и лимита cgroup, и ограничен диапазоном 64..512 МиБ; при неизвестном объёме берётся 64 МиБ. Новая сессия резервирует 256 КиБ, а при нехватке бюджета сервер отвечает HTTP 503 (`docs/ninelives.md:28-55`). Версии 2 и 3 протокола зарезервированы: сервер отклоняет версию 2 или 3, ненулевые `caps` и `suite = 2`, а не пытается перейти на них (`docs/xhttp-protocol.md:191-213`). С XHTTP из Xray это расширение не совместимо.

## П.7. CatTail

CatTail версии 1 есть необязательная внешняя оболочка уже существующего TLS-потока. Клиент шлёт зашифрованные и дополненные кадры на отдельный TCP-слушатель endpoint, сервер снимает оболочку и передаёт внутренние байты тому же TLS-приёмнику, что и на основном порту. Клиент включает CatTail настройкой ключа, сервер держит слушатель из секции `[cattail]`; диапазон портов к этому слушателю приводит правило DNAT или redirect на хосте, а клиент выбирает случайный порт диапазона для каждого нового TCP-подключения. Ключ оболочки удостоверяет только внешний слой и не заменяет HTTP-авторизацию внутри (`docs/cattail.md:1-16,263-288` серверного дерева).

*Таблица П.8. Устройство кадра CatTail; nonce стоит не в кадре, а перед первым кадром своего направления, остальные смещения отсчитываются от начала кадра*

| Смещение | Поле | Длина | Значение |
|---|---|---|---|
| 0 | `E(header)` | 48 | AES-128-GCM от 32 байт открытого заголовка и тега 16 |
| 48 | mid padding | `mid_len` | не аутентифицируется, получатель пропускает |
| 48 + mid | `E(body)` | `body_len + 16` либо 0 | шифротекст внутренних байтов и тег; при `body_len = 0` поля нет |
| после body | end padding | `end_len` | не аутентифицируется, получатель пропускает |
| перед первым кадром | `N_c` либо `N_s` | 24 | nonce своего направления: `N_c` клиента, `N_s` сервера |

Перед первым кадром каждой стороны идёт её nonce из 24 байт: `N_c` в начале клиентского потока и `N_s` непосредственно перед первым ответным кадром после допуска, в той же записи. Общий ключ `K` есть 32 байта; в ссылке он передаётся тегом `0x58` в виде байтов, а в текстовой форме и в конфигурации сервера `[cattail] key` записывается base64. Расшифрованный заголовок занимает 32 байта: `type:u8` при 0 (OPEN `0x01` или DATA `0x02`), `version:u8 = 1` при 1, `timestamp:u64` при 2, `identity:u64` при 10, `counter:u48` при 18, `body_len:u16` при 24, `mid_len:u16` при 26, `end_len:u16` при 28, `reserved:u16` при 30. Поля `timestamp`, `identity` и `counter` заполняет только OPEN, в DATA они нулевые; `reserved` посылают нулём и не читают. Длина тела не выше 16384, длины набивки лежат в 0..65535, а при нулевом теле нет ни шифротекста, ни тега, и счётчик не растёт. HKDF-SHA256: `key_c2s = Expand(Extract(salt=N_c, IKM=K), "cattail-v1 c2s", 16)`, `key_s2c = Expand(Extract(salt=N_c||N_s, IKM=K), "cattail-v1 s2c", 16)`, где `||` есть конкатенация. Nonce AEAD состоит из направления (`0x01` клиент → сервер, `0x02` сервер → клиент), трёх нулевых байтов и счётчика `u64`. В каждом направлении один счётчик начинается с нуля: заголовок расходует очередное значение, непустое тело следующее, пустое тело значение не расходует. AAD пуст (`docs/cattail.md:47-130`, `lib/src/cattail.rs`).

```text
 client: N_c + OPEN + DATA --> CatTail listener (separate TCP port)
                                | decrypt OPEN, check key,
                                | version, size, time, replay
                                +-- reject: close, no response
                                +-- accept: inner bytes --> TLS acceptor
 client <-- N_s + DATA ---------+
             (only after admission)
```

*Рисунок П.7. Внешняя оболочка и приём первого кадра*

Первый клиентский кадр всегда OPEN, все следующие кадры в обе стороны DATA. Тело OPEN уже может нести первые байты внутреннего TLS; после допуска сервер передаёт их и тела следующих DATA TLS-приёмнику, не сохраняя границы CatTail. Для внутреннего потока важен только порядок байтов (`docs/cattail.md:87-136`). Поле `identity` клиент выбирает случайно при каждом запуске, а `counter` этой личности растёт на каждом новом TCP-подключении. Сервер проверяет расшифрованный OPEN по ключу, типу, версии, размеру, времени и отсутствию повтора. `timestamp` в секундах Unix отличается от времени сервера не больше чем на 120 с и не старше запуска слушателя; пара `identity` и `counter` повторно не допускается в окне последних 1024 значений (`docs/cattail.md:139-180`). До допуска сервер не пишет ни байта, а при отказе молчит и закрывает соединение через случайные 10-60 с (когда молчащих соединений больше 4096, сразу); после допуска повреждение любого кадра закрывает соединение (`docs/cattail.md:181-199`).

Схема набивки есть набор строк `key=value`, разделённых переводом строки или `;`; пробелы вокруг ключа и значения не значат ничего. Отправка (`write`) есть порция внутренних байтов, переданная слою CatTail: у сервера это одно чтение со стороны TLS. Ключ `stop=0..16` задаёт число первых отправок, которые формируются по схеме; строка `i=` для отправки `i` содержит до 16 элементов через запятую. Элемент `lo-hi` или `n` (то же, что `n-n`) задаёт полный размер кадра на проводе в диапазоне 48..16448. Из этого размера 48 байт уходит на заголовок и тег, 16 на тег тела, поэтому при размере не меньше 65 и непустых данных кадр несёт `min(|D|, L - 64, 16384)` байт данных, а остаток размера идёт в набивку; при размере меньше 65 кадр состоит из одной набивки. Элемент `c` прекращает разбор элементов, если данные кончились. Остаток данных и все отправки без строки идут обычными DATA-кадрами: тело до 16384 байт, набивка из диапазонов ключей `mid=` и `end=` (каждый в пределах 0..4096; у сервера по умолчанию `mid=0-32`, `end=0-96`). Самый первый кадр клиента и в этом случае OPEN. Ключ `nonce=lo-hi` заменяет первые `P` байт собственного nonce, где `P` выбирается в этих границах от 0 до 24, печатными символами ASCII 0x21..0x7E, остальное остаётся случайным. Неизвестный ключ игнорируется, а неверный известный ключ, строка без `=` или номер отправки 16 и больше делают схему недействительной целиком: сервер отказывается стартовать, клиент берёт встроенную схему (`docs/cattail.md:203-261`). Положительные и отрицательные примеры лежат в `docs/cattail-pattern-contract.json:1-24`, криптографические векторы в `docs/cattail-vectors.json`.

## П.8. HTTP/2 padding и Анти-DPI

Эти механизмы меняют видимые размеры и сегментацию соединения, но не вводят нового формата данных приложения. Набивка HTTP/2 работает после рукопожатия внутри уже установленного TLS-соединения, а Анти-DPI меняет отправку первого ClientHello на уровне TCP (`docs/padding.md:3-24`, `docs/anti-dpi.md:3-5` репозитория приложения).

*Таблица П.9. Что меняется на проводе*

| Уровень | Поле/сегмент | Длина и значение |
|---|---|---|
| HTTP/2 HEADERS/DATA | флаг PADDED, длина набивки и байты набивки | при включённой маскировке первые 2-4 кадра каждого потока получают по 1-64 байта; бюджеты по умолчанию 2048 байт на поток и 4096 на сессию |
| TCP под TLS | границы первого ClientHello | одна TLS-запись разбита на TCP-сегменты |
| TCP urgent | внеполосный байт `-o` | за ним обязателен сегмент `-d` с малым TTL |
| IP | TTL выбранного сегмента `-d` | TTL 1; после потери на первом маршрутизаторе ОС повторно отправляет те же байты с обычным TTL |

```text
 ClientHello: [one TLS record with SNI]
      |-- -s N or -o N: split before byte N
      |-- -d N: bytes before N sent with TTL 1, then resent
      +-- server receives one ordinary TLS stream

 HTTP/2 after handshake: HEADERS / DATA + PADDED
      +-- receiver removes padding (RFC 9113)
```

*Рисунок П.8. Разные уровни изменения формы соединения*

Кадр с флагом PADDED следует RFC 9113: получатель обязан снять набивку, поэтому серверу ничего настраивать не нужно. Маскировка размеров есть переключатель «Маскировка размеров (HTTP/2)» в настройках ключа, по умолчанию выключенный; включение ставит максимум четыре кадра на поток, остальные значения доступны рядом. Движок выбирает случайное число начальных кадров потока от минимума 2 до этого максимума и добавляет к каждому от 1 до 64 байт, пока не исчерпан бюджет потока или сессии. Если «считать на каждый поток» выключено, набиваются только первые кадры всей сессии, ровно заданное максимумом число (`docs/padding.md:16-44`).

Анти-DPI включается отдельно, действует только для TCP и не меняет HTTP/3. Режим 1 применяет `-o3 -d7`, режим 2 `-d7`, режим 3 `-o1+s -d3+s`; автоматический режим перебирает 1, 2 и 3 (по два за попытку) и запоминает удачный для пары «сервер и сеть» до местной полуночи. В своей строке `-s N` делит поток перед байтом N обычным разрывом TCP, `-o N` добавляет срочный байт, `-d N` отправляет часть записи с TTL 1. Отсчёт N идёт от начала TLS-записи; отрицательное N считается от конца записи, а суффикс `+s` (он же `+h`) от начала имени в SNI. Части, которые не попадают строго внутрь записи после предыдущей, пропускаются. Низкий TTL теряет ранний сегмент на первом маршрутизаторе, и ОС позже повторяет его с обычным TTL. Одинокий urgent оставил бы серверный читатель в ожидании, поэтому `-o` без следующего за ним `-d` не принимается, а выпавший при разметке `-d` превращает `-o` в обычный разрыв (`docs/anti-dpi.md:9-54` репозитория приложения, `docs/features.md:96-103` серверного дерева). Строку проверяют три набора правил: валидатор плагина, разбор в ядре и тесты обеих сторон; неверная строка не сохраняется и не импортируется, а ядро отклоняет ключ целиком, а не подключается без обхода. Деление ClientHello на несколько TLS-записей (`-r`) в этой версии не поддерживается.
