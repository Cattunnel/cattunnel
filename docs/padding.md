# Маскировка размеров (HTTP/2 padding)

Длины первых записей TLS после рукопожатия видны наблюдателю без расшифровки. У туннеля они складываются в узнаваемый рисунок: первый запрос `CONNECT`, ответ сервера, первые данные. Маскировка размеров добавляет к первым кадрам каждого потока HTTP/2 случайные байты, чтобы этот рисунок менялся от потока к потоку.

## Как это работает

Механизм стандартный: флаг PADDED кадров HTTP/2 (RFC 9113, раздел 6.1). Получатель обязан принять и отбросить добавленные байты, поэтому сервер ничего не настраивает: работает и с [сервером CatTunnel](https://github.com/Cattunnel/cattunnel-server), и с обычным сервером TrustTunnel. Действует только для HTTP/2 (TCP); для HTTP/3 (QUIC) настройка ни на что не влияет.

Решение принимает формирователь трафика ядра (`traffic_shaper` в сетевом ядре):

1. Для каждого нового потока (одно соединение приложения = один поток `CONNECT`) ядро выбирает случайное число кадров от «минимум» до «максимум».
2. Каждый из этих первых кадров HEADERS или DATA получает случайное число байт в заданных пределах. Байт длины набивки входит в это число.
3. Набивка ограничена бюджетом на поток и бюджетом на всю сессию HTTP/2. Когда бюджет кончился, кадры идут без набивки.

Каждый поток начинается одинаково, поэтому первый поток сессии не отличается по форме от двадцатого. В проверенной конфигурации ядра каждый кадр HTTP/2 уходил отдельной записью TLS, так что набивка меняла длину записи на проводе байт в байт. Для других размеров кадров это отдельно не проверялось.

Набивка уменьшает различие в распределении длин записей, но не делает туннель неотличимым от браузера: порядок записей и их ритм остаются своими.

## Настройки

Переключатель «Маскировка размеров (HTTP/2)» находится в настройках сервера, раздел «Для экспертов». По умолчанию выключен. Включение ставит максимум 4 кадра на поток; там же доступны остальные значения.

| Настройка | Ключ ядра | Тег `tt://` | По умолчанию в приложении |
|---|---|---|---|
| Кадров на поток, максимум | `h2_padding_frames` (0 = выключено, до 64) | `0x44` | 0, при включении 4 |
| Кадров на поток, минимум | `h2_padding_frames_min` | `0x46` | 2 |
| Считать кадры на каждый поток | `h2_padding_per_stream` | `0x47` | да |
| Набивка в кадре, от байт | `h2_padding_min_bytes` | `0x48` | 1 |
| Набивка в кадре, до байт | `h2_padding_max_bytes` (до 256) | `0x49` | 64 |
| Бюджет на поток, байт | `h2_padding_stream_bytes` | `0x4A` | 2048 |
| Бюджет на сессию, байт | `h2_padding_session_bytes` | `0x4B` | 4096 |

Если «считать на каждый поток» выключено, ядро набивает только первые кадры всей сессии, а не каждого потока.

Подписка может задать все эти значения ключу (теги выше). Если тега нет, остаётся значение приложения. Ключ с переключателем «Выше подписки» подписка не трогает.

Роутерная редакция передаёт ядру только `h2_padding_frames`; остальные значения там берутся из ядра по умолчанию (1-256 байт на кадр, 2048 байт на поток, 8192 на сессию).

## Что ещё меняет форму трафика

- Заголовки запроса `CONNECT` в ядре такие же, как у браузера Chrome, поэтому сжатый HPACK первый запрос близок по размеру к браузерному.
- Сервер CatTunnel отвечает на `CONNECT` с правдоподобными заголовками (`date`, `server`, `cache-control` и два случайных идентификатора случайной длины).
- Пул соединений распределяет потоки по 2-4 TLS-соединениям и открывает их с паузами: [anti-dpi.md](anti-dpi.md#пул-соединений).
