# Маскировка размеров (HTTP/2 padding)

Длины первых записей TLS после рукопожатия видны наблюдателю без расшифровки. У туннеля они складываются в узнаваемый рисунок: первый запрос `CONNECT`, ответ сервера, первые данные. Маскировка размеров добавляет к первым кадрам каждого потока HTTP/2 случайные байты, чтобы этот рисунок менялся от потока к потоку.

В TrustTunnel такой возможности нет: ядро клиента не добавляет набивку. Это отличие CatTunnel, оно работает только в клиенте.

## Как это работает

```text
 поток CONNECT: кадр 1   кадр 2   кадр 3   кадр 4   кадр 5 ...
 набивка:       +17 Б    +4 Б     +52 Б    нет      нет
                \_ первые 2-4 кадра (случайно), пока есть бюджет _/
 на проводе: длина TLS-записи = кадр + набивка
```

Рисунок 1. Набивка первых кадров одного потока. Числа в примере случайные.

Механизм стандартный: флаг PADDED у кадров HEADERS и DATA (RFC 9113, раздел 6.1). Получатель обязан принять и отбросить добавленные байты, поэтому сервер ничего не настраивает: работает и с [сервером CatTunnel](https://github.com/Cattunnel/cattunnel-server), и с обычным сервером TrustTunnel. Действует только для HTTP/2 (TCP). Для HTTP/3 (QUIC) настройка ни на что не влияет.

Решение принимает формирователь трафика ядра (`traffic_shaper` в `net/src/traffic_shaper.cpp`, обратный вызов `select_padding_callback` в `net/src/http2.cpp`):

1. Для каждого нового потока (одно соединение приложения означает один поток `CONNECT`) ядро выбирает случайное число кадров от «минимума» до «максимума».
2. Каждый из этих первых кадров получает случайное число байт в заданных пределах. Байт длины набивки входит в это число.
3. Набивка ограничена свободным местом в кадре, бюджетом на поток и бюджетом на всю сессию HTTP/2. Когда бюджет кончился, кадры идут без набивки.

```text
 новый поток -> цель = случайно(мин. кадров .. макс. кадров)
 кадр готов  -> набито кадров < цели ?
                  да:  набивка = случайно(мин. байт .. макс. байт)
                       набивка = min(набивка, место в кадре,
                                     остаток бюджета потока,
                                     остаток бюджета сессии)
                       отправить кадр с набивкой, счётчик кадров + 1
                  нет: отправить кадр как есть
```

Рисунок 2. Решение для каждого кадра.

Каждый поток начинается одинаково, поэтому первый поток сессии не отличается по форме от двадцатого. Размер кадра HTTP/2 равен размеру TLS-записи, поэтому набивка меняет длину записи на проводе байт в байт.

Набивка уменьшает различие в распределении длин записей, но не делает туннель неотличимым от браузера: порядок записей и их ритм остаются своими.

## Настройки

Переключатель «Маскировка размеров (HTTP/2)» находится в настройках ключа, раздел «Для экспертов». По умолчанию выключен. Включение ставит максимум 4 кадра на поток; там же доступны остальные значения.

| Настройка | Ключ ядра | Тег `tt://` | По умолчанию в приложении |
|---|---|---|---|
| Кадров на поток, максимум | `h2_padding_frames` (0 выключает, до 64) | `0x44` | 0, при включении 4 |
| Кадров на поток, минимум | `h2_padding_frames_min` (до 64) | `0x46` | 2 |
| Считать кадры на каждый поток | `h2_padding_per_stream` | `0x47` | да |
| Набивка в кадре, от байт | `h2_padding_min_bytes` (до 256) | `0x48` | 1 |
| Набивка в кадре, до байт | `h2_padding_max_bytes` (до 256) | `0x49` | 64 |
| Бюджет на поток, байт | `h2_padding_stream_bytes` | `0x4A` | 2048 |
| Бюджет на сессию, байт | `h2_padding_session_bytes` | `0x4B` | 4096 |

Если «считать на каждый поток» выключено, ядро набивает только первые кадры всей сессии, а не каждого потока.

Бюджеты ядро ограничивает числом 1048576. Пока маскировка включена, приложение записывает в настройки ядра все семь значений, и они заменяют умолчания ядра. Если какого-то значения в настройках ядра нет, ядро берёт своё: 2 кадра минимум, по потокам, от 1 до 64 байт на кадр, 2048 байт на поток и 4096 на сессию.

Подписка может задать все эти значения ключу (теги выше). Если тега нет, остаётся значение приложения. Ключ с переключателем «Выше подписки» подписка не трогает ([subscriptions.md](subscriptions.md)).

Роутерная редакция передаёт ядру только `h2_padding_frames`, остальные значения там берутся из ядра по умолчанию.

## Что ещё меняет форму трафика

- К запросу `CONNECT` ядро добавляет заголовки, которые браузер шлёт с навигационным запросом (`accept`, `accept-encoding`, `accept-language`, `sec-ch-ua*`, `sec-fetch-*`, `upgrade-insecure-requests`, `priority`). TrustTunnel отправляет только `user-agent` и `proxy-authorization`. Благодаря сжатию HPACK первый запрос сессии получается большим, а следующие маленькими, как у браузера (функция `put_browser_headers`). В `user-agent` стоит не строка браузера, а платформа и имя приложения.
- Сервер CatTunnel отвечает на `CONNECT` заголовками обычного веб-сервера (`date`, `server`, `cache-control` и два случайных идентификатора случайной длины), а не пустым ответом одного и того же размера.
- Пул соединений распределяет потоки по 2-4 TLS-соединениям и открывает их с паузами: [anti-dpi.md](anti-dpi.md#пул-соединений).
